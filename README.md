# Proposal Portal Astra

정보시스템 감리 제안팀의 인력·사업 조회, 본문 PPT 및 첨부서류 제작을 지원합니다.

## 실행 환경과 연결 대상

- GitHub: https://github.com/sweatmoon/proposal-portal-astra
- Astra 운영 주소: https://proposal-portal-proposal-portal-astra.up.railway.app/
- Hono + Node.js + PostgreSQL, Docker/Railway 배포
- 사진·회사 증빙·인력 서류는 Synology NAS에서 조회
- Cloudflare 관련 초기 파일이 남아 있으나 현재 실행 대상은 Node.js입니다.
- 본문 1차 개선 `ed62fc0`은 GitHub에 푸시했습니다. 이번 사진 조회/다운로드 수정은 로컬 검증 단계이며 운영 반영은 별도입니다.
- 운영 DB 및 원본 저장소는 변경하지 않습니다.

## 주요 경로

- `/`: 현황 대시보드
- `/proposals`, `/proposals/:id`: 사업 목록·상세, 본문 PPT 모달
- `/personnel`, `/personnel/:id`: 인력·경력 조회
- `/upload`: HTML 적재
- `/ppt-templates`: 목차·템플릿 관리
- `/ppt-generate`: 첨부서류 생성
- `/api/ppt-menus?category=proposal`: 본문 목차·등록 템플릿 조회
- `/api/ppt-menus/master-templates/active`: 활성 마스터 조회
- `POST /api/personnel/photo-images`: 읽기 전용 사진 일괄 조회, JSON `{ "names": ["이름"] }`, 요청당 1~100명. 인력별 `ok`, `dataUri` 또는 `error`, `stage`, `code` 반환
- `GET /api/personnel/photo-image-by-name?name=이름`: 인력 ID 없이 이름으로 사진 조회
- `GET /api/personnel/:id/photo-image`: 기존 ID 기반 사진 조회
- `/health`: 서버 상태

## 본문 PPT 개선

- 사업 데이터에 대상사업명·기간, RFP 요구공수·단계·일수 전달
- 감리원 MD를 단계별 인력 배정에서 합산하여 중복 계산하지 않음
- `public/static/proposal-template.js`: 본문 전용 XML 치환·계산·검증
- 여러 텍스트 런으로 나뉜 토큰과 반복 토큰 처리, XML 특수문자·주변 문구 보존
- 공통 사업명·주관기관·대상사업 토큰 연결
- 일정 계획: 일반 4단계·상주/상시 1단계, 고정 분야 슬롯, 5개월·연도 치환
- 세부 일정: 등록 양식 사용, 미사용 단계 블록 제거, 상주/상시·검수지원 구분, 배정 MD 합계 반영
- 예비조사·조치확인 일수는 MD로 임의 역산하지 않고 확인 필요 표시
- 조치확인: post MD가 있는 인력을 단계별 열에 배치, 최대 3단계·15명 제한
- 사진 장표의 2/4/6/9인 슬롯·페이지 복제 유지
- 목차별 생성·실패·미치환 보고서 유지. 일부 목차 실패나 경고가 있어도 생성된 장표는 확인창 없이 다운로드
- 생성된 장표가 전혀 없거나 합본 자체가 실패하면 오류 표시. 빈 파일을 완료로 표시하지 않음
- 다른 목차의 구형 합본으로 조용히 대체하지 않음
- RFP 공수 비교 범위를 담당자가 선택하기 전에는 충족을 확정하지 않음
- 인력 자격은 증빙 판단 로직이 없으므로 검토 필요
- 합본 미디어 ContentType·외부 링크 보존, 마스터 ID 충돌 방지

## 사진 조회 수정

- 폴더 목록 API에 의존하지 않고 `증명사진(이름).png`를 직접 다운로드합니다. 목록 조회 실패 때문에 전원 사진 다운로드를 포기하던 흐름을 제거했습니다.
- NAS 로그인/로그아웃은 일괄 요청당 한 번, 다운로드는 최대 3개 동시 실행합니다. 같은 Node 프로세스의 사진 배치는 순차 처리합니다.
- 세션 만료·네트워크 오류는 한 번 재시도하며 이미 성공한 사진은 다시 받지 않습니다.
- 이름 기반 API를 `/:id`보다 먼저 등록하여 `400 invalid id` 충돌을 해결했습니다.
- ID 미연결 인력도 이름으로 조회하고, ID=0인 여러 사람이 하나로 합쳐지지 않게 처리합니다. TBD는 조회하지 않습니다.
- 로그인/다운로드 단계와 Synology 오류 코드를 보존합니다. 권한·인증·네트워크 실패를 실제 사진 없음으로 표시하지 않습니다.
- 응답의 PNG 시그니처를 확인합니다. HTTP 200 + JSON 오류를 사진으로 삽입하지 않습니다.
- 기본 NAS 경로는 유지합니다. 실제 NAS 공유 경로가 다르면 선택 변수 `NAS_PHOTO_FOLDER`로 서버 측 설정이 가능합니다. PC의 SynologyDrive 로컬 경로가 아니라 NAS File Station 경로를 사용합니다.
- 목록 조회와 무관하게 파일 자체의 읽기 권한은 필요합니다. NAS 권한을 우회하는 기능이 아닙니다.
- NAS 실서버의 직접 다운로드 성공은 아직 확인하지 않았습니다. 배포 후 사진 API 결과로 확인해야 합니다.

## 사용 방법

1. 인력·사업 HTML을 적재하고 사업 상세 화면을 엽니다.
2. 자동화 PPT 모달에서 추가 단계와 사진 장표 구성을 선택합니다.
3. RFP 최소공수 비교 범위를 확인합니다. 미확정이면 요약표는 검토 필요입니다.
4. 생성 버튼을 누르면 생성 가능한 장표를 합쳐 검토용 PPT로 바로 다운로드합니다. 다운로드 확인창은 없습니다.
5. 화면의 목차별 실패·미치환·사진 조회 경고를 확인합니다.
6. PowerPoint에서 고정 문구·사진·도식·표 넘침·RFP 근거를 최종 검수합니다.

## 데이터 및 보안

- PostgreSQL: 인력·경력·사업·단계 배정·템플릿·규칙 저장
- NAS: 사진·원본 증빙자료 조회, 이번 변경에서 파일 수정 없음
- 신규 DB 마이그레이션 없음
- `DATABASE_URL`, `NAS_BASE_URL`, `NAS_USERNAME`, `NAS_PASSWORD`는 Railway Variables 또는 로컬 `.env`에서 관리합니다. 자격증명을 커밋하지 마세요.
- 사진 API와 로그에 NAS 비밀번호·SID·응답 원문을 출력하지 않습니다.
- 사용자가 정상화한 Astra DB 스키마는 변경하지 않았습니다. 저장소의 기존 스키마만으로 운영 DB를 재생성하지 마세요.

## 미완성 범위와 다음 단계

- 전체 38개 목차의 사업별 동적 작성은 완성되지 않았습니다.
- 미등록 템플릿 목차는 실패로 표시합니다.
- `MANPOWER_MD` 전용 양식·생성기 연결이 필요합니다. 인력 실적표를 공수표라고 대체 출력하지 않습니다.
- 일정 막대·화살표 배치, 고정 수행기한 문구 및 현재 양식 용량을 넘는 단계 확장은 미구현입니다.
- 조직도·비율·총괄 요건·교육·회사 실적 등의 규칙 확정이 필요합니다.
- 전체 RFP 해석, 자격·증빙 판정, PowerPoint 시각 검수는 자동 검증 범위가 아닙니다.
- 템플릿 API의 Base64 일괄 로드는 유지됩니다.
- 실제 검증용 사업의 PPT 시각 검수와 NAS 사진 실서버 확인이 다음 단계입니다.

## 개발 및 검증

```sh
npm ci
npm test
npm run build
```

28개 테스트는 합성 데이터·메모리 PPTX·모의 NAS 응답을 사용하며 운영 DB/NAS에 접근하지 않습니다. 사진 직접 다운로드, 오류 구분, 세션 재시도, 일괄/이름 라우팅, 미연결 인력 매칭, 확인창 없는 부분 PPT 다운로드를 포함합니다.

이전 수동 확인: 운영 템플릿을 GET으로 읽어 합성 인력을 적용한 사진·경력 제외 20개 목차의 XML 치환을 확인했습니다. 실제 PowerPoint 렌더링 검수와는 다릅니다.

## 배포

- Dockerfile이 TypeScript를 컴파일하고 정적 파일을 `dist/static`에 복사합니다.
- GitHub 연결 자동 배포가 활성화되어 있으면 푸시가 Railway 배포를 유발할 수 있습니다. 별도 승인 전 푸시하지 않습니다.
- 원본 `sweatmoon/proposal-portal` 및 원본 production DB는 변경 대상이 아닙니다.
